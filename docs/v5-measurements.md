# v5 measurements

Date: 2026-09-19.
`solarsql build` prints one line per module, but no number exists for a project of tens of modules and hundreds of statements past the three-module example.
This experiment builds a generated project at five (module count, statements-per-module) sizes and reports what the build itself measures.

Command:

```
node spike/12-build-scale.ts
```

Machine: Apple M4, 32 GB RAM, macOS 26.5.2.
Node v26.7.0, SQLite 3.53.4 (node:sqlite).

Each size runs twice against a fresh temporary project; the table reports the second run, so file-system and V8 warmup do not count.
Every module has one table (a text primary key, a text column that references the previous module's table when there is one, two more text columns, one integer, one real), one index, and a mix of select/join/paging queries and insert/update/delete commands, split evenly.
The join query reads a non-key column of the previous module's table, so every module but the first carries `readsAll: true` (ADR 0009's boundary check requires it).
"overhead ms" is total time minus the sum of the per-module times the build prints: the engine construction from every module's DDL and the migration status diff, both sized by module count, not by statement count.

| N | M | total ms | module ms (median) | module ms (max) | overhead ms | entries/module | generated bytes |
|---|---|---|---|---|---|---|---|
| 1 | 10 | 8 | 5 | 5 | 3 | 14 | 4885 |
| 5 | 20 | 51 | 7 | 8 | 14 | 27 | 8919 |
| 20 | 20 | 188 | 7 | 12 | 41 | 27 | 8919 |
| 50 | 20 | 521 | 8 | 11 | 106 | 27 | 8919 |
| 20 | 100 | 693 | 30 | 34 | 74 | 134 | 43581 |

Conclusions:

- The median and max per-module time stay flat as N grows (5-50 modules at M=20: 7-12 ms), so a module's own typing cost does not grow with the module count around it.
- Overhead grows close to linearly with N: 5→20 modules (4x) is 14→41 ms (2.9x); 20→50 modules (2.5x) is 41→106 ms (2.6x). Nothing in this range is clearly super-linear.
- Growing M instead of N (20→100 statements per module, 5x, at N=20) moves the per-module time from 7 to 30 ms (about 4x) and leaves overhead roughly flat (41→74 ms), matching overhead's source being module count, not statement count.
- These runs shared the machine with other concurrent work in the same repository checkout; absolute milliseconds vary run to run (a repeat of the N=20, M=20 case ranged from 138 ms to 742 ms across attempts), but the flat-per-module, linear-overhead shape held in every run. No hot spot was profiled, since no size was clearly super-linear.
