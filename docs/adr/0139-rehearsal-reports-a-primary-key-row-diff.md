# ADR 0139: rehearsal reports rows inserted, updated, and deleted, by primary key

Status: accepted (2026-09-25). Extends ADR 0057 (rehearse's own authorizer denies ATTACH and DETACH): the row diff below is the one place that authorizer now allows both, narrowly. Adds a field the way ADR 0119 already added `columns` at `version: 1` (CHANGELOG.md).

## Context

`rehearse.md:4` says rehearsal proves a migration applies "without losing rows," but the code never checked that: a plain `delete from customers where id='c3'`, an `insert or ignore` rebuild that loses a row, and an `upper(name)` rewrite all returned `ok: true` with no diagnostic (measured with `rehearseSnapshot`). `rehearse.md:29` and `:72` already say row counts and a successful case do not prove value preservation; the skill's own walkthrough (`sql-workflow.md:94-97`) has an agent hand-write `count(*)` and `sum(amount)` assertions for exactly this reason.

The SQLite session extension (`node:sqlite`'s `createSession`/`changeset`) was measured against solarsql's own generated rebuild shape (`example/migrations/0005_customer_name_not_empty.sql`, Node 26.7.0 and 24.18.0): for a table a foreign key references, with foreign keys on, the changeset is an exact diff; for a leaf table, or with foreign keys off, every re-inserted row reports as an INSERT (500,000 unchanged `orders` rows gave 500,000 inserts, 15.4 MB); for a rebuild that drops a column, `changeset()` throws "not an error" (errcode 0). A report whose correctness depends on foreign-key topology is a silent wrong result, so this was rejected.

What was measured to work instead: a primary-key diff in SQL against a before-copy. Leaf rebuild unchanged 0/0/0; value rewrite updated 2; lost row deleted 1; column-dropping rebuild 0/0/0 over the remaining columns without throwing; backfill of 666,666 rows updated 666666. Cost scales linearly: 100k rows, copy 17ms and diff 64ms; 400k rows, 65ms and 259ms (Node 26.7.0).

## Decision

`rehearseSnapshot()` takes its own before-copy with `db.prepare('vacuum into ?').run(path)`, on the working connection, before `begin` and before any authorizer is installed -- a deny-all authorizer (already in place for the rest of the rehearsal) denies VACUUM INTO too, since it performs its own internal `SQLITE_ATTACH` (measured: "authorization denied", action 24). This one path serves both `rehearse()`'s own on-disk snapshot flow and a direct in-process `rehearseSnapshot()` caller; no second copy is taken from the original source (two VACUUM INTOs of a live WAL source with a commit between them were measured to give different copies).

The diff runs last: after every check and assertion, before commit. The authorizer that has denied ATTACH and DETACH for the whole rehearsal (ADR 0057) is replaced, only for this stage, with one that allows `SQLITE_ATTACH` when its first argument equals the before-copy's own file path exactly, and `SQLITE_DETACH` only for a fixed reserved schema name (`solarsql_rehearse_before`); every other ATTACH or DETACH, and the same PRAGMA denials ADR 0057 already has, stay denied. No proposed SQL runs after this point. The narrower authorizer can still see, during the row diff, a statement the caller did not write: a function the caller registered on the db, called from a generated column's expression, can issue nested statements while the diff reads that column, and each of them passes through this authorizer. So it denies every ATTACH other than the before-copy's own path, and every DETACH other than the reserved schema name, rather than relying on the diff to be the only source of either (measured with node:sqlite). Only a direct `rehearseSnapshot()` caller can register such a function; `rehearse()` opens its own copy with none registered.

For each table present, by name under SQLite's identifier case rule, both before and after, and not a virtual table or one of a virtual table's own shadow tables (the `type` column of `pragma main.table_list`) on either side:

These identifier matches fold ASCII letters, as SQLite does, and preserve case differences in non-ASCII letters such as `Ä` and `ä`.

- A primary key match is required: the same number of primary-key columns on both sides, each with a same-name counterpart under that rule. A table with no primary key, or whose primary-key columns changed, gets `{ compared: false, reason }` instead of counts.
- Every remaining common column (matched by name under that rule) is compared with `a.c IS NOT b.c COLLATE BINARY OR typeof(a.c) IS NOT typeof(b.c)`: measured, plain `IS NOT` alone misses an `upper()` rewrite on a `COLLATE NOCASE` column (0 vs 2) and misses an integer-to-real or TEXT-to-INTEGER retype (0 vs 2); this pair catches both. The primary-key join itself carries no `COLLATE` override, so it runs under each column's own declared collation and can use its own index; a `NOCASE` primary key therefore matches keys case-insensitively here too.
- `inserted` uses an anti-join against the before-copy. `updated` counts after rows with no value-equal before match, and `deleted` includes unmatched and merged before rows.
- A before row that matches two or more after rows makes the diff unreliable because the diff cannot select one continuation.
- When two or more before rows match one after row, the extra before rows count directly as deleted. When no before row matches two or more after rows, `before + inserted - deleted = after` follows from these counts, so the row counts add no separate check.
- The primary-key join uses `IS`, not `=`: a rowid table can store NULL in a non-`INTEGER` primary-key column, and `=` never matches NULL to NULL (measured: an untouched NULL-keyed row was reported as both inserted and deleted). If more than one row shares the same NULL-inclusive primary-key tuple on either side -- the only way a duplicate tuple can exist at all, since SQLite's own PRIMARY KEY/UNIQUE index forbids a duplicate that has no NULL -- the table gets `{ compared: false, reason }` instead of counts, since `IS` cannot match those rows one-to-one.

Cleanup, in `finally`: rollback first (DETACH fails inside an open transaction with "database ... is locked"); then the authorizer is cleared before the DETACH attempt (not kept at the narrow ATTACH-stage allowance), so a run that never reached the diff stage still gets SQLite's own "no such database" for a schema that was never attached, rather than an authorization denial that would mask it -- no proposed SQL runs after this point, so clearing the authorizer early exposes nothing; a DETACH failure other than "no such database" is recorded as a diagnostic without changing `result.ok`; the before-copy's own temporary directory is removed last. Windows cannot remove the open file when DETACH fails, so a removal failure adds `TEMP_CLEANUP_FAILED` with the remaining path and original error without changing `result.ok`.

The new field, `rows: Record<string, { compared: true; inserted: number; deleted: number; updated: number } | { compared: false; reason: string }>`, is added at the existing `version: 1`, the way ADR 0119 added `columns` there.

### A lost or changed row fails by default (owner decision, 2026-09-27)

A rehearsal fails when a compared table's own row diff shows `deleted > 0` or `updated > 0`, or when a `compared: false` table has fewer rows after than before, unless `checks.json` declares the table under `expected`. The declaration follows `dropped`'s and `retyped`'s own shape (arrays under `expected`), as two more keys, `deleted` and `updated`, each an array of `{ table }`: unlike a dropped or retyped column, a lost or rewritten row is never scoped to one column, so a per-column entry would claim a precision the diff cannot back, and a single combined key (naming only the table) would let a reviewed backfill's `updated` declaration also pre-authorize an unreviewed `deleted` on the same table -- the same pre-authorization risk `unmatchedSchemaShape`'s own stale check already refuses for `dropped`/`retyped`. An entry the migration did not produce is a stale failure too, the same as `dropped`/`retyped`.

A `compared: false` table cannot report a deleted or an updated count, but a row count that shrank is still evidence of a loss, so it is checked against `expected.deleted`; `updated` carries no signal there, since a `compared: false` table's rewritten values are invisible either way. A table that stays the same size or grows is not flagged: `compared: false`'s own reason already says its contents cannot be verified, and a delete-and-insert pair that keeps the row count steady could still hide inside it -- only a per-row comparison could catch that, and that comparison is exactly what `compared: false` means the diff could not do.

A dropped column already excludes that column from the diff's common-column set, so the value it carried away never counts as `updated` (unaffected by this decision, confirmed by `test/rehearse.test.ts`'s "rows compares over the columns a rebuild kept" test).

`expected.retyped` on a column excuses only the type change itself, not any value change alongside it (owner amendment, 2026-09-27, correcting two earlier versions of this decision). The first version excluded the whole retyped column from the comparison, so a value wiped to NULL or a lossy cast in the same rebuild was excused too. The second version dropped `COLLATE BINARY` as well as `typeof` from that column's predicate (a bare `a.c IS NOT b.c`); measured, a retyped column also declared `COLLATE NOCASE` or `COLLATE RTRIM` in the rebuild then compares under that collation, not binary, so a genuine rewrite that only changed case or trailing whitespace passed as "value-preserving" too.

`diffTable`'s `updated` predicate reads `a.c IS NOT b.c COLLATE BINARY OR typeof(a.c) IS NOT typeof(b.c)` for every common column (this ADR, above). For a column `expected.retyped` names, the count this check uses instead drops only the `typeof` disjunct, keeping `COLLATE BINARY`: `a.c IS NOT b.c COLLATE BINARY` alone. `COLLATE BINARY` governs only the collating sequence used for a text-to-text comparison; it does not disable SQLite's own comparison affinity conversion between a TEXT-affinity value and a NUMERIC-affinity value, so an integer retyped to the text of the same number still compares equal (`5 IS NOT '5' COLLATE BINARY` is false, the same as it would be for `5 = '5'`), while a value actually rewritten -- a case change, a lossy cast, a wipe to NULL -- still compares unequal regardless of either column's own declared collation. This predicate is strictly weaker than the full one (it only ever drops the `typeof` disjunct, never adds a way to detect a difference it did not already catch), so a table whose full `updated` count is 0 always has this narrower count at 0 too. A row whose retyped column's value differs even after affinity conversion still counts, needing its own `expected.updated` entry the same as any other column; a different column's own change on the same row is never excused by a retype declared on some other column, since only the columns `expected.retyped` names get the narrower predicate. `expected.retyped` never excuses `deleted`: a row vanishing is not implied by any column's type changing.

Both counts -- the reported `updated` and this check's narrower count -- come from one query per table. Each aggregate counts after rows that have no value-equal before match. A merged row can continue from an unchanged candidate, while other candidates count as deleted. `diffAllTables` takes the caller's `expected.retyped` columns, grouped by table, and returns this narrower count alongside `rows`, so the enforcement stage (`unmatchedRowChanges`, below) only ever compares counts and never touches the database itself.

`expected.retyped`'s column name matches `schemaShapeFindings`' own retyped finding by the before-side column's name -- the same name `unmatchedSchemaShape`'s own stale check already requires the entry to match -- so a rebuild that changes a retyped column's case (`Qty` to `qty`) is recognized consistently by both checks.

The new stage, `ROWS_LOST_OR_CHANGED`, runs last, after `result.rows` is computed and before commit, the same position `SCHEMA_SHAPE_CHANGED` (ADR 0119) already established for a schema-level finding. Its message lists every unexpected finding and every stale declaration together, `<kind> <table> (<count>)` or `<kind> <table> (before <n>, after <n>)` per item, the same one-message-per-run convention `SCHEMA_SHAPE_CHANGED` uses.

`rehearse.md:4` is corrected: a lost or changed row now fails the rehearsal by default, not only reports.

## Consequences

- Build facts, migration introspection, the rehearsal, and runtime `migrate()` read the main catalog with PRAGMA statements, so an object named after a pragma table function, which shadows that function, cannot hide tables or row loss.
- `ok: true` no longer hides a lost or changed row: a compared table's own `deleted > 0` or `updated > 0`, or a `compared: false` table's shrunk row count, fails the rehearsal unless `checks.json` declares it under `expected.deleted` or `expected.updated`.
- A virtual table (e.g. FTS5) and its own shadow tables never appear in `rows`; a table with no primary key, or a rebuild that changes the primary key, appears with `compared: false` and a reason instead of counts.
- `rehearseSnapshot()` is no longer free of filesystem access (it now takes its own VACUUM INTO copy); every filesystem call it makes stays synchronous, so a caller driving it from a property test still needs no async scheduling.
- Cost scales with row count (measured linear, tens of ms per 100k rows); a rehearsal against a very large table pays for the copy and the diff even when nothing changed.
