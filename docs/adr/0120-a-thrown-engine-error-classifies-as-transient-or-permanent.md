# ADR 0120: A thrown engine error classifies as transient or permanent

Status: accepted (2026-09-19)

## Context

A constraint failure and a failed assert already come back as values, never thrown (ADR 0082 reads a thrown value defensively and rethrows it, but does not classify it). `running.md` says: "An engine error is thrown; the adapters do not retry an operation whose commit outcome is unknown. Use an application idempotency key or reconciliation before repeating a write after a lost response." That line names the two choices, retry or reconcile, but gives a caller nothing to choose from: D1 and a Durable Object each throw platform text, and a Worker author has to already know that "Durable Object is overloaded" means the request never ran, while "no such column" means it never will.

The following pages were fetched and read on 2026-09-19:

- D1 debug page (`https://developers.cloudflare.com/d1/observability/debug-d1/`, last updated 2026-08-11): gives the worked `D1_EXEC_ERROR` example (a misspelled keyword surfaces `sql error: near "INSERTZ": syntax error ...`), the `D1_TYPE_ERROR` and `D1_COLUMN_NOTFOUND` rows, and a "List of D1_ERRORs" table with a recommended action per message. The action says "Retry the operation" for: "Cannot resolve D1 DB due to transient issue on remote node.", "Network connection lost.", "Replica disconnected from primary.", "D1 DB reset because its code was updated.", "Internal error while starting up D1 DB storage caused object to be reset.", "Internal error in D1 DB storage caused object to be reset." Two messages get a different action, not "retry": "D1 DB is overloaded. Requests queued for too long." and "D1 DB is overloaded. Too many requests queued." both say "App action: Optimize the queries..., send fewer requests..., or shard the queries," and "D1 DB storage operation exceeded timeout which caused object to be reset." says the same. The page also warns that retrying is only safe for an idempotent query, and that D1's own automatic retry only ever applies to a read.
- D1 platform limits page (`https://developers.cloudflare.com/d1/platform/limits/`): describes the same "overloaded" error as the result of a full request queue; no message text beyond what the debug page already lists.
- Durable Object troubleshooting page (`https://developers.cloudflare.com/durable-objects/observability/troubleshooting/`, last updated 2026-05-15): "Durable Object is overloaded." (four variants, each with an `.overloaded` property, meant to be caught so an application does not blindly retry into more overload), "Your account is generating too much load on Durable Objects. Please back off and try again later." (a stub lookup, safe to retry after a short wait since lookups are cached), "Durable Object reset because its code was updated." ("Reset" refers to in-memory state; durable state already persisted through `state.storage` is unaffected, which says nothing about a request that was in flight at the moment of reset), "Durable Object storage operation exceeded timeout which caused object to be reset." (the page names one call, `deleteAll()`, as safe to retry because it makes progress each time; it does not make that claim for a write in general), "Your account is doing too many concurrent storage operations. Please back off and try again later." (back off; prefer a batched read).
- Durable Object storage API page (`https://developers.cloudflare.com/durable-objects/api/storage-api/`): describes the output-gate behavior behind a reset -- a failed write discards outgoing messages and restarts the object -- which confirms a reset can happen after a write already started, but adds no new message text.
- Workers observability errors page (`https://developers.cloudflare.com/workers/observability/errors/`): repeats "Network connection lost" with the generic advice "Catch a fetch or binding invocation and retry it," with no mention of D1 or Durable Object -specific codes beyond that.
- SQLite's own result-code reference (`https://sqlite.org/rescode.html`, checked 2026-09-19): `SQLITE_BUSY` "indicates that the database file could not be written (or in some cases read) because of concurrent activity by some other database connection"; `SQLITE_LOCKED` names the same conflict within one connection instead of between two. The page also notes `SQLITE_BUSY` "can occur at any point in a transaction," not only at the start, which this module's plain, unqualified `SQLITE_BUSY` rule does not distinguish from the not-yet-started case.

None of these pages states, for "Network connection lost," "Replica disconnected from primary," the two "Internal error ... caused object to be reset" messages, or a Durable Object's own code-update reset, whether the statement already reached the engine before the connection or the object was lost. Each recommends "retry" only in the sense of retrying the request, not in the sense that a write is safe to repeat blindly; solarsql cannot tell a caller "not applied" for any of these without risking a duplicate write. This ADR calls that outcome unknown instead, matching `running.md`'s own existing rule to reconcile before repeating a write.

## Decision

`src/runtime/failure.ts` exports one pure function, `failureClass(error: unknown)`, re-exported from the package root:

```ts
export type FailureClass =
  | { kind: "transient"; outcome: "not_applied" | "unknown"; reason: string }
  | { kind: "permanent"; reason: string }
  | { kind: "unclassified" };
```

A rule table, each entry a `{ reason, test, class }` on `bareMessage(error)` (the existing D1 prefix and extended-code stripping in `src/runtime/plan.ts`, now exported for reuse instead of duplicated), sorts a message into `not_applied` when the cited page's own account says the platform refused the request before it reached storage, `unknown` when the page does not say so or explicitly describes a reset or a lost reply mid-flight, and `permanent` when the text is a SQL error the engine or a D1 error code documents. `not_applied` names only that the request never ran; two of its messages ("Durable Object is overloaded." and "D1 DB is overloaded.") come with an action that says to send fewer or cheaper requests, not "retry" -- this function reports what it can confirm and leaves the retry decision, and its pacing, to the caller (ADR 0030). A message that names a constraint kind `constraintFailure()` cannot resolve to a target is `permanent`: the engine still applied a known kind of rule. A Durable Object reset-and-rolled-back wrapper (the same wrapper `bareMessage()` already strips before returning its result, so `failure.ts` keeps its own copy of that one pattern to test for the wrapper's presence, since `plan.ts` exports only `bareMessage()` and `errorDetails()` for this task, not the pattern itself) is `permanent` too, whether or not its text resolves to a known constraint: the wrapper's own text states both the cause ("constraints were violated") and the outcome ("reset and rolled back to its last known good state", so nothing from the request applied); what this module cannot always name is which constraint. Anything no rule matches, including a thrown value that is not an `Error` or carries no string message, is `unclassified`; the function never throws.

`reason` is a short stable label for the rule that matched, not the message text, so a caller can `switch` on it and a log can group by it.

`failureClass()` does not retry, sleep, or wrap an adapter call. Retry stays the caller's decision (ADR 0030); this function only removes the part of that decision that required reading Cloudflare's own error text by hand.

## Evidence

`test/failure-class.test.ts`: one example case per rule, using the exact text quoted above (plus SQLite's own `SQLITE_BUSY` and `SQLITE_LOCKED` text, from `https://sqlite.org/rescode.html`, checked 2026-09-19), a case for the D1_ERROR prefix, a case for the Durable Object reset wrapper stripped before a rule runs, a case for the wrapper with a resolved constraint underneath and one with an unresolved constraint underneath (both permanent), and a case proving the rule order: a message carrying both an unresolved constraint phrase and a trailing `SQLITE_` code reports `unresolved_constraint`, not the `sqlite_code` catch-all. A Hegel property covers arbitrary thrown values (`null`, `undefined`, a number, a string, a plain object, an `Error` with a random message): `failureClass()` always returns a value with a valid `kind`, and never throws. A second property covers an `Error` with a random string message: any non-`unclassified` result is traceable to a known substring the drawn message actually contains, so a rule cannot match text it was not written for.

## Consequences

- `running.md`'s "Values across adapters" section replaces its two retry sentences with a table naming each message or prefix, the platform, the class, the outcome, what a caller does, and the source page and date, plus a six-line sample calling `failureClass()` in a catch block.
- A future Cloudflare error message this module does not yet know about returns `unclassified`, the same as any other message no rule matches; nothing here guesses.
- The five pages fetched for this decision agree with each other everywhere they overlap; none contradicted another. One page did qualify its own general "retry" framing: the Durable Object troubleshooting page's `.overloaded` property exists so an application can avoid retrying an overloaded request outright, and the D1 debug page gives "optimize the queries" or "shard," not "retry," for both of its own "overloaded" messages. `not_applied` reports only that the request never ran; it does not read as this module's advice to retry immediately.
- `sqlite_code` and the "no such table" / "no such column" half of `sqlite_no_such` are not literal quotes from any of the five fetched pages; they generalize from `src/runtime/plan.ts`'s own comment that the engine's text passes through D1 and a Durable Object unprefixed, and from the one pass-through example (a different SQLite message) the debug-d1 page does show. `src/runtime/failure.ts`'s comments say so at each rule.
