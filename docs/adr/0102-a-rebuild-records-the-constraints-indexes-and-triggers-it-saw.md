# ADR 0102: A rebuild records the constraints, indexes, and triggers it saw

Status: accepted (2026-09-15)

## Context

ADR 0101 has a table rebuild record each column's normalized declaration text, and has replay refuse a rebuild whose recorded declaration no longer matches the column's actual one. That decision covers a column's own shape only; it does not cover what else a `DROP TABLE` takes down with it.

A rebuild's `CREATE TABLE` (`src/build/migration.ts`'s `tableStatements()`) is built from the rebuilding branch's own target schema. A table-level constraint — `CHECK`, a table-level `UNIQUE(...)`, a named `CONSTRAINT`, or a table-level `FOREIGN KEY` — appears in the new `CREATE TABLE` only if that branch's own target declares it; `diff()` knows nothing of a constraint a sibling branch added independently. An index or a trigger is dropped along with the table by `DROP TABLE` itself, and is recreated only if the rebuilding branch's own target schema declares it (`diff()`'s `createLast.push(index.sql)`, and the equivalent for triggers). This is the same root cause ADR 0099 and ADR 0101 already named — a rebuild's `CREATE TABLE` comes from a schema snapshot, not the live schema — reaching further than a column's own declaration.

Three reproduced scenarios follow from this, all against the real generator and replay functions:

- Branch A adds a table-level `CHECK`; branch B, independently, adds a table-level `UNIQUE`. Neither changes a column's own declaration, so ADR 0101's check does not see either change. Replaying B then A leaves the table with only A's `CHECK`; B's `UNIQUE` is gone, with no refusal.
- Branch B adds an index, with no rebuild of its own. Branch A, for an unrelated reason, rebuilds the same table. Replaying B then A drops the index along with the table, and A's `CREATE TABLE` never recreates it, because A's target schema never declared it.
- The same shape as the index case, with a trigger in place of the index. A trigger can carry data-integrity behavior, such as keeping a search table in sync, so its silent loss can be more consequential than an index's.

## Decision

`RebuildRecord` (`src/build/scan.ts`) gains three fields: `constraints`, `indexes`, and `triggers`, each a `string[]`. `constraints` is `Table.constraints` as `definitions()` already returns it: normalized text, one entry per table-level constraint, with no further normalization applied when it is recorded or compared. `indexes` and `triggers` are drawn from `Schema.indexes` and `Schema.triggers`, filtered to the rebuilding table, each entry `normalize(sql)` of the index's or trigger's own `CREATE` statement; unlike `constraints`, this normalization is applied both when the value is recorded and when it is read back for comparison, because these values start as unnormalized `CREATE INDEX`/`CREATE TRIGGER` text, not as an already-normalized fact the way `Table.constraints` is.

Replay compares each recorded set against the table's actual set, immediately before the rebuild's statements run, through one new function, `unknownDeclaration(recorded, actual)` (`src/build/scan.ts`), shared by `applied()` (`src/build/migration.ts`) and `migrate()` (`src/durable.ts`) rather than duplicated in each. The comparison is one-directional, the same direction ADR 0099 already established for a column: it refuses only when the actual set has an entry the recorded set does not, meaning something was added since generation that the rebuild's own statements do not know to recreate. An entry present in the recorded set but absent from the actual set is not a refusal, for the same reason a single rebuild's own intentional drop of a column is not one under ADR 0099: refusing on that direction too would also refuse the ordinary, legitimate case where a rebuild removes its own constraint, index, or trigger on purpose. This direction has a real consequence beyond a single rebuild's own drop, covered below.

A table-level constraint has no name a `RebuildRecord` could key on the way a column has. Recording and comparing all three as a set of declaration text, rather than as a map keyed by name, needs no separate case for the unnamed one, and keeps one comparison, and one shared function, for all three kinds of declaration.

## Why

ADR 0101 already established that a column's name being known to a rebuild does not mean its shape is; this decision applies the same lesson one level up, to declarations a rebuild's own `CREATE TABLE` does not carry at all unless its own target schema names them. A table-level constraint, an index, and a trigger share that exposure, so one comparison, run for all three, closes it, instead of a fix scoped to only one of the three reproduced scenarios above.

## Consequences

- `render()`'s output changes only for a migration that rebuilds a table: the recorded JSON gains three fields. A migration with no rebuild is unchanged, byte for byte.
- A `FOREIGN KEY` is already covered, not newly exposed by this gap: a column-level `REFERENCES` is part of that column's own `.def`, which ADR 0101's check already compares, and a table-level `FOREIGN KEY` clause is a table-level constraint, which the new `constraints` set now covers.
- The one-directional comparison does not refuse a rebuild whose recorded set has an entry the actual set lacks: when a sibling migration has dropped a table-level constraint, an index, or a trigger that this rebuild's own target schema still declares, replaying this rebuild restores it, with no refusal, because its `CREATE TABLE` and `createLast` statements run from its own target schema, not from the live one. A dropped column does not share this exposure the same way: a rebuild's own copy statement selects that column from the source table, so a sibling's column drop still surfaces as a real SQLite error (`no such column`) rather than a silent restoration. Refusing this direction too is a separate decision, since it would also refuse the ordinary case of a rebuild dropping its own constraint, index, or trigger on purpose; it needs a way to tell "a sibling dropped this on purpose" apart from "this rebuild's own generator saw it dropped," which the current record does not carry.
- A trigger's recorded text and its replay-time actual text both pass through `normalize()`. `render()`'s `triggerForD1()` uppercases a trigger body's `BEGIN`/`END` for D1 compatibility; `normalize()` already erases exactly that case difference, empirically confirmed against the real tokenizer, so this check does not refuse a trigger against its own D1-rewritten copy.
- Naming which earlier migration file added a constraint, an index, or a trigger, the way ADR 0099's `firstIntroducedBy` names which file added a column, is not part of this decision; the refusal here names the file being replayed, the declaration's kind and name (an index or a trigger, read with `created()`; a constraint has no name to report), and the declaration's full normalized text.
- A file `render()` wrote under ADR 0101's format — with a `RebuildRecord` that has no `constraints`, `indexes`, or `triggers` field — fails the new parser's validation, the same way a file written under ADR 0099's format already fails ADR 0101's validation: `parseRebuildRecords` drops the whole record, not only the three new fields, so such a file replays with no rebuild check at all, columns included, the same boundary ADR 0101 already drew for an ADR 0099-format file.
