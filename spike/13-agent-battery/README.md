# Agent battery

Nothing measures agent outcomes today. This battery gives a fresh agent a broken project and one task, then measures: repair success, files read, failed commands, and wall time to a passing `build --check`.

Five scenarios repair a break, each in `scenarios.ts`: an invalid column in a query, a query edited without a rebuild, a column added to the schema only, a write into another module's table from the wrong module, and a column rename declared without its migration intent. Each `setup` breaks a fresh copy of `example/`, states one task, and `check` verifies the repair against the library's own rules (`build --check`, `npx tsc --noEmit`, and the scenario's own shape).

Two more scenarios add a feature instead of repairing a break, on a larger, generated project instead of `example/` -- see "The two arms" below.

`starter.ts` builds the fresh copy: `test/copy-example.ts`'s `copyExample`, with the skill at `.claude/skills/solarsql/` (where a Claude Code agent looks for it) and the same three-sentence project note in both `AGENTS.md` and `CLAUDE.md` (Claude Code reads `CLAUDE.md`, not `AGENTS.md`). Two `node_modules/.bin` shims (`solarsql`, `tsc`) forward to this repository's own source, so `npx solarsql build` and `npx tsc --noEmit` -- the commands the skill and the build's own "next:" line name -- resolve inside the starter with no network install.

After a scenario's `setup` runs, `run.ts` calls `starter.ts`'s `finalizeStarter`: a passing `test/smoke.test.ts`, and the starter's own git repository (the setup's mutation as the one committed baseline) -- three saved streams showed an agent spending over half its tool calls on git commands that resolved past the starter to this repository, and a search for tests, before either existed.

Metrics come from the agent CLI's own event stream (`--output-format stream-json`), not from file-system watching: the same source for every agent, needing no OS support. `metrics.ts` is the only file that knows that shape; a different agent CLI needs only a new parser with the same `Metrics` return type. Reads count a distinct `Read` `file_path`, plus one for each `Glob` or `Grep` call; edits count a distinct `Edit` or `Write` `file_path`; failed commands count every `tool_result` with `is_error: true`; cost and turns come from the stream's final `result` line (`total_cost_usd`, `num_turns`), `null` when the agent does not report them.

`run.ts` also saves a `.diff` of what the agent changed (see "Options" below); `hunksOutsideTask` (`metrics.ts`'s `countHunksOutsideTask`) counts its hunks whose added or removed lines name a table outside the scenario's own `taskTables` -- a harmful edit, one the task did not ask for. A hunk counts only when it names one of the scenario's `knownTables` (its full table set), not any word: a migration file's own boilerplate comment ("Generated by solarsql from the declared schema") would otherwise read as a table named "the".

## The two arms

Does module ownership -- a module owns its tables; another module writes to them only through the owner's commands -- reduce harmful edits as a project grows? `owned-cross-module` and `flat-cross-module` run the same task on the same generated 12-module project (`spike/12-build-scale.ts`'s `writeProject`, N=12, M=20 -- M has no default there; 20 is what that file's own `main` uses for every N past its single-module case): once with one module per table (`owned`), and once with every table concatenated into one module (`flat`, `scale-project.ts`'s `writeFlatProject` -- so no module-boundary check applies to a write).

The task: give the customer table (`t10`) a `deleted_at` column, and make deleting a customer also remove its rows in the table that references it (`t11`, via `parent_id` -- the only pair spike/12's generator gives an actual foreign key between; the spec that asked for this study named modules 3 and 7, which this generator does not relate, so the task adapts to the pair that is actually related). `check` requires: `build --check` and `tsc --noEmit` pass, a migration adds `deleted_at`, and a functional check (`cascade-check.ts`, run in a separate process by `cascade-check-worker.ts`) passes.

The check replays the migrations, inserts one customer row and one referencing row, then finds by structure -- not by name -- a command in the referencing module whose plan deletes from the referencing table through a parameter, preferring one that deletes by the column naming the parent; it tests each candidate on its own fresh database and keeps the first that clears the rows, so declaration order inside the catalog cannot pick the wrong command. It then runs that command, finds a command in the customer's module that deletes the customer by id, runs that too, and asserts both rows are gone; a single flat-arm command whose plan does both is found and accepted at each step. A `t10` row a soft-delete command leaves behind, with `deleted_at` set, fails the check with a message that says the task asked for a delete and the row remains.

That functional check does not exercise a command whose plan needs an unrelated parameter, and it never finds an `on delete cascade` foreign key across the two modules, because the build itself refuses one here: deleting a `t10` row would then also delete `t11` rows through a command `t10` does not own, the same rule that refuses a direct write. A correct owned-arm fix is necessarily two commands, one per module, not one plan, one trigger, or a cascading foreign key.

The check runs in its own process, not the process that built the starter: that process already imported the starter's `module.ts` and `solarsql.generated.ts` once while establishing the pre-task baseline, and a later in-process re-import of the same path -- after the task's fix rewrote those files -- returns Node's cached, pre-fix module instead of the fix.

```
node spike/13-agent-battery/run.ts --agent "<command>" --scenario owned-cross-module --runs 3 --out .scratch/owned-out
node spike/13-agent-battery/run.ts --agent "<command>" --scenario flat-cross-module --runs 3 --out .scratch/flat-out
```

## Running with the stub

`stub-agent.ts` is a scripted fixer, not a model. Its purpose is to prove the harness: setup breaks the project, and the check catches a wrong fix (`SOLARSQL_BATTERY_SKIP_FIX=1` makes it apply no fix; the run then reports `success: false` with a `checkFailure` string).

```
node spike/13-agent-battery/run.ts --agent "node spike/13-agent-battery/stub-agent.ts" --out .scratch/battery-out
```

`test/slow/agent-battery.test.ts` runs this over all seven scenarios and pins the stub's `filesRead`, `filesEdited`, `failedCommands`, and `hunksOutsideTask` per scenario, since the stub's fix is scripted and so is what it reads, writes, and runs.

## Running with Claude Code

```
node spike/13-agent-battery/run.ts --agent "claude -p --model sonnet --output-format stream-json --verbose --permission-mode acceptEdits --allowedTools Read,Edit,Write,Bash,Glob,Grep --setting-sources project" --out .scratch/battery-out
```

This runs a paid model, once per scenario per `--runs`; vary `--model` to compare models. The owner starts it, not an agent working in this repository. `--setting-sources project` matters: without it, a headless run also loads the operator's own `~/.claude` hooks and instructions into the agent under test, not just the starter's own `CLAUDE.md`.

## Options

```
node spike/13-agent-battery/run.ts --agent "<command>" [--scenario <name>] [--runs <n>] [--out <dir>]
```

`--out` gets `metrics.jsonl` (one JSON line per run, with `costUsd` and `turns` alongside the other fields) and, on stdout, a markdown table of scenario, runs, success, median files read, median files edited, median failed commands, median hunks outside task, median duration, and median cost (USD). The command exits 1 when any run failed.

Each run also gets two files, named on its `metrics.jsonl` line as `streamPath` and `diffPath`: `<scenario>-<run>.stream.jsonl` is the agent's raw stdout, saved before it is parsed, and `<scenario>-<run>.diff` is a `git diff --no-index` of the agent's finished project directory (`example/`, or `scale/` for the two cross-module scenarios) against a second starter built with the same `scenario.setup` (not the repository's own `example/`, since `setup` already differs from it -- diffing straight against the repository would mix the scenario's own break into what the agent changed). Together they answer why one scenario cost more tool calls than another, which the counted numbers alone cannot.

```
node spike/13-agent-battery/summarize.ts <out>/<scenario>-<run>.stream.jsonl
```

Prints one line per tool call, in the order the agent made it: the tool name, its main argument (`file_path`, `command`, or `pattern`, truncated to 120 characters), and `FAILED` when the matching `tool_result` reported an error -- then the agent's own final result text.
